01 / CLAIM

先说清楚，要检查什么。

声明是待检查的文字；证据要求是另一件事。每条 claim 用标识、回执引用和适用范围，说明它依赖什么。

声明文本+证据引用+适用范围

模型的自报置信度不是门控输入。required 标记这条声明是否需要证据。

数据加载后，在这里阅读所选 fixture 的 claim_id、text、evidence、scope 与 required。核心说明可直接阅读。

02 / TOOL

保留工具的输入与输出。

03 / RECEIPT

把一次调用封装成可核对字段。

回执记录输出哈希、输入摘要、时间戳、nonce 和签名。verifier 可以据此检查记录是否符合演示约束。

内容摘要·时间 / nonce·演示签名

HMAC 使用公开的 demo key，只演示字段绑定，不能证明来源身份。失败样例中的空字段和重复值会原样保留。

展开全部回执字段 receipts

数据加载后显示所选输入中的每一份回执，包括失败记录。

04 / BINDING

让证据引用落到具体回执。

claim 的 evidence 引用回执 ID，scope 标记声明范围。契约的 provenance 则保留 verifier 实际返回的溯源摘要。

claim→receipt_id 引用→provenance

存在引用不等于证据已验证。这里并排展示输入与返回值，不在浏览器判断绑定是否成立。

展开引用、范围与溯源 evidence / provenance

数据加载后显示 claim 引用、policy 范围及原始 provenance_summary。

05 / GATE

遇到失败，就在这里返回。

门控消费声明与回执，检查工具、回执字段、引用、范围和覆盖率。实际判定由现有 Python verifier 完成，网页只读取构建时保存的结果。

没有逐项执行日志。verifier 在首个失败处分支返回；后续检查不能视为已运行。六步导览也不代表内部判定顺序。

规范与实现的部分缺失引用处理存在差异。本站呈现实际 contract；覆盖率、阈值和溯源计数分别原样展示，不据此重算结论。

展开策略与记录的返回值 policy / contract

数据加载后显示 fixture clock、演示 policy、decision 与 detail_code。

06 / CONTRACT

把结果交给下一个调用方。

同一个 contract 里包含 decision、原因、证据覆盖率、溯源摘要和升级路径。调用方可以据此区分三类返回值。

decision+reason / detail+escalation_path

这是返回值的设计与离线样例；外部 agent 在真实任务中能否可靠消费它，仍需要验证。

02 / 读懂返回值

拒绝，也需要说清楚原因。

三个结果回答不同的问题。页面用文字和字段解释状态，颜色只是辅助。

可接受

accept

在当前演示策略下，回执通过检查且覆盖率达标。

不等于声明在现实世界中为真。

测量失败

MEASUREMENT_FAILURE

工具或回执出了问题，例如哈希不符、过期、重放或缺少回执。

先处理测量问题，再考虑结论。

证据不足

INSUFFICIENT_EVIDENCE

回执可用，但证据仍不足以支持声明，例如覆盖率未达阈值。

需要补证据或按契约转人工。

04 / 把边界留在明处

一个窄接口。
仍有未回答的问题。

可以复现，不代表已经证明。这个原型的价值在于让输入、返回值与局限可以一起被检查。

01

离线数据，固定时钟

全部为本地 fixture / 合成演示，使用 fixture clock。没有 live 结果；页面也不运行新实验。

02

公开密钥，只演示绑定

公开 HMAC demo key 不能证明来源身份。不能由这些记录推出生产级安全，也没有密钥轮换、撤销或可信时钟保证。

03

重放检查不持久

nonce / receipt_id 的已见集合只存在于一次 verifier 调用中，不提供跨进程的持久重放防护。

04

契约之外，保留未知

工具输出在世界上是否为真、模型是否理解、H1 / H2 是否成立，都不能由这七个 fixture 证明。
